# deerflow.storage.backends-档案

## 一、这个包是干什么的

这个包是blob存储后端的容器。

blob存储的契约在`deerflow/storage/contract.py`。
契约是抽象的。
真正的存储能力由后端提供。

这个包本身几乎没有代码。
它只有一个`__init__.py`。
它只写明后端的放置规则。

这个包是插件机制的一部分。
添加新后端的方式是往这里放一个文件夹。
不需要改任何其他deer-flow代码。

后端的drop-in契约是这样的。

- 文件夹名等于后端名。
- 后端名等于`BlobStorageConfig.backend`的值。
- 每个`__init__`暴露`STORE_CLASS`。
- `STORE_CLASS`是`BlobStore`的子类。

工厂通过扫描这个目录发现后端。
这就是drop-in机制的实现。

## 二、包里的主要成员

### （一）模块__init__.py——放置规则说明

这个模块是纯文档性的。
它定义后端契约的入口约定。

每个子包是一个自包含的后端。
每个子包在自己的`__init__`里暴露`STORE_CLASS`。
`STORE_CLASS`是`BlobStore`的子类。

drop-in契约的内容。

- 文件夹名就是后端名。
- 后端名就是配置里`blob_storage.backend`的值。

添加新后端的方式。

- 往这里放一个新文件夹。
- 在配置里设置`blob_storage.backend: <name>`。
- 不需要改其他任何deer-flow代码。

深度规则在上级AGENTS.md里。
布局、发布规则、可移植性、点分路径逃生口都在那里。
保留和垃圾回收的交互在docs/blob-storage.md里。

### （二）后端发现机制

工厂的`_scan_backends`扫描这个目录。

扫描规则。

- 跳过下划线开头的目录。
- 每个候选目录必须含`__init__.py`。
- 有`__init__.py`的目录才被导入。
- 导入后读取`STORE_CLASS`属性。
- 属性必须是`BlobStore`的子类。
- 满足条件的注册进registry。

一个坏的可选后端不会拖垮整个store。
导入失败只记录日志，继续扫描其余后端。

### （三）设计意图

这个包的存在让添加后端变成纯增量动作。

不用注册表文件。
不用中央配置。
不用修改工厂代码。
放个文件夹就行。

这和memory后端的drop-in契约一致。
memory的manager也用同样的文件夹扫描模式。
两个系统共享同一种扩展方式。

## 三、它和谁协作

上游是`deerflow/storage/manager.py`。
工厂扫描这个目录发现后端。
工厂通过`STORE_CLASS_ATTR`找到类。

下游是具体后端。
目前有local_fs。
local_fs是默认后端。
内容寻址的文件存储。

未来的后端也放这里。
S3是文档里提到的一个候选。
任何实现`BlobStore`契约的类都可以成为后端。

它和配置系统协作。
`blob_storage.backend`的值就是文件夹名。

## 四、重要性评级

评级：3分。

理由如下。

这个包本身几乎没有代码。
它只是一个放置约定。
一个`__init__.py`说明drop-in规则。

它不在任何路径上。
运行、智能体、工具都不经过它。
工厂扫描的是它的目录，不是它的代码。
删除它的`__init__.py`会让扫描跳过所有后端。
但当前只有local_fs一个后端。

它的重要性是结构性的。
它定义了添加后端的扩展点。
扩展点本身代码量是零。
没有扩展点的说明文档，添加后端的人不知道往哪放。

所以给3分。
结构性重要，运行时无影响。
删掉文件夹和说明，local_fs还能通过点分路径被引用。
工厂的注册名机制受损，但功能可用。
