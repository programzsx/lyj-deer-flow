# PluginTargetError-档案

# 一、这个类是干什么的

PluginTargetError定义在`backend/packages/harness/deerflow/authz/plugin_targets.py`。

这个类是一个异常类。这个类继承自`ValueError`。

这个类表示"插件资源目标无法从宿主校验过的组件拼出来"。

要理解这个类。先要理解它所在模块的职责。

模块docstring说明了模块定位。

这个模块是组合插件授权目标的唯一编码方。

插件授权要判断的目标是`"{namespace}/{part}"`这种组合字符串。

左边是插件命名空间。右边是具体组件。

模块的所有者原则是：任何调用点不允许用字符串拼接构造目标。

任何生产方必须调用三个构造函数之一。

构造函数校验两个部分。

校验不通过就抛PluginTargetError。

构造函数不会返回一个"尽力而为"的字符串。

这个设计的目标是：生产方和读取方永远不在编码或校验上有分歧。

命名空间的字符集排除了`/`。所以组合字符串没有歧义。

# 二、类的成员（字段、方法，各自做什么）

## （一）继承与定位

这个类继承自`ValueError`。

这个类没有定义任何新字段。这个类没有定义任何新方法。

这个类就是`ValueError`的一个语义化子类。

语义化子类的好处是调用方可以精确捕获。

调用方捕获`PluginTargetError`就知道是"目标拼装失败"。

调用方捕获`ValueError`就分不清是目标问题还是别的校验问题。

异常消息由`_join`函数构造。消息里包含无效的值和期望的模式。

## （二）抛出这个类的函数

模块里有三个构造函数会抛这个异常。这三个函数都走内部的`_join`函数。

- `plugin_action_target(namespace, action_name)`：为注册的插件后端动作构造目标。`_join`校验命名空间和动作名。命名空间模式是`[a-z][a-z0-9_.-]{0,95}`。这个模式镜像宿主注册规则。动作名模式是`[a-z][a-z0-9_-]{0,63}`。这个模式镜像注册后端动作规则。校验失败抛PluginTargetError。
- `plugin_page_target(namespace, surface_id)`：为声明的插件页面构造目标。`_join`校验命名空间和页面ID。页面ID模式是`[a-z][a-z0-9-]{0,63}`。这个模式镜像前端模块的surface-id规则。校验失败抛PluginTargetError。
- `plugin_management_target(namespace, part)`：为管理读/写检查构造目标。`_join`校验命名空间和管理部分。管理部分只接受`permissions.read`或`permissions.write`。校验失败抛PluginTargetError。

`_join`内部函数先校验命名空间。再校验右半部分。任何一半不合法就抛PluginTargetError。两半都合法才返回`"{namespace}/{part}"`。

# 三、它和谁协作

这个类是目标构造函数的失败信号。

上游关系如下。

`_join`函数抛出这个异常。三个构造函数都经由`_join`。

生产方如下。

模块docstring列出了生产方。生产方是注册动作的分发器、页面投影、管理守卫、资源目录。这些生产方调用三个构造函数。组件不合法时构造函数抛出这个异常。

读取方如下。

读取方是授权提供者和企业策略。读取方读目标字符串做策略匹配。

消费关系如下。

调用方可以捕获这个异常做兜底处理。因为它是`ValueError`的子类。捕获`ValueError`也能捕获它。

读取方不捕获这个异常。读取方读到的目标已经是合法编码。

这个类自身不依赖任何其他类。这个类只依赖Python内置的`ValueError`。

# 四、重要性评级（1-10分+理由）

评级：4分。

理由如下。

这个类是编码契约的失败信号。

没有它，构造函数只能抛裸的`ValueError`。

调用方就分不清"目标拼装失败"和"其他校验失败"。

它的存在让"禁止字符串拼接"这条规则有了强制力。

构造函数宁可抛错也不返回坏目标。

这个设计防止生产方和读取方在编码上分歧。

但是这个类本身非常薄。

这个类没有字段。这个类没有方法。这个类只是`ValueError`的语义标签。

删掉它，模块改用`ValueError`也能工作。只是失去精确捕获的能力。

依赖它的地方是三个构造函数。

使用面窄。体量极小。

它服务于一个重要的正确性目标。但它是辅助角色。

所以给4分。
