# deerflow.config.file_signature-档案

## 一、这个模块是干什么的

这个模块是配置文件的内容签名助手。

有的配置文件是运行时可改的。

系统需要检测这些文件什么时候真的变了。

只比较mtime是不够的。

同一秒内的编辑、mtime不动的编辑、`git checkout`或`cp -p`让mtime回退，这些情况bare mtime都会漏判。

这个模块用`(mtime, size, sha256)`三元组做签名。

这样上述漏判都能被抓住。

这个模块是唯一实现，两个调用点共享同一个行为。

## 二、模块里的主要成员

### 1、ConfigSignature类型

这是签名三元组的类型别名。

三个元素是mtime、size、sha256十六进制摘要。

摘要为None表示文件状态读取成功但内容读不出来。

整个三元组为None表示文件根本不存在。

### 2、get_config_signature()

获取文件的签名。

stat失败返回None。

内容读失败返回部分签名。

这里总是哈希完整文件，不做短路。

原因是同秒内换入等长的不同内容，mtime和size都不变。

只有sha256能抓住这种偷换。

### 3、read_config_with_signature()

读一次文件，同时返回内容和这份内容的签名。

这个函数解决一个竞态。

调用方先解析文件再探测签名，两次读之间如果来了写入，就会把一个版本的签名记到另一个版本的内容上。

缓存会永远提供陈旧内容，而且签名比较抓不到。

因为磁盘上的签名已经对上了。

用这个函数，解析的字节和记录的签名来自同一次读。

任何写入最终都会表现为一次签名不匹配，多一次重载。

stat在读取之前做，稳定文件的两个助手给出相同签名。

文件缺失或读不出来会抛OSError。

## 三、它和谁协作

`app_config.py`用它做config.yaml的签名检测。

`managed_models.py`用它做加密目录的签名检测。

`mcp/cache.py`用它做extensions配置的缓存陈旧检测。

## 四、重要性评级

评级：7分。

理由：热重载的正确性建立在这个模块上。签名竞态的注释解释了非常细的边界情况。这是"多个调用点必须共享一份实现"的典型解耦。
