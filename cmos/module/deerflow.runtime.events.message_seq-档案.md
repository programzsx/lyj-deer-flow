# deerflow.runtime.events.message_seq

## 一、这个模块是干什么的

这个模块解决消息定位问题。

背景是这样的。

检查点里不存序列号。

线程消息流里存了序列号。

客户端把检查点和消息流合并展示。

合并时需要按序列号排序。

但有一种情况拿不到序列号。

情况是客户端只是打开一个对话。

客户端没有看到任何流帧。

它通过REST读检查点。

没有序列号，较早的消息就只能按最近的锚点排。

压缩之后这个锚点可能排到很深的位置。

这是一个真实缺陷，编号是4666。

这个模块是worker打戳器的请求侧对应物。

检查点里还留着的消息都已经持久化了。

所以一次批量查询就能解析整个列表。

不需要事后重试。

这个模块的设计原则是降级而不是报错。

定位是增强功能。

拿不到序列号时客户端回退到自己的排序规则。

## 二、模块里的主要成员

- stamp_messages_with_seq(store, thread_id, messages)：核心函数。返回带序列号的消息列表。
- 输入永远不会被修改。拿到序列号的条目是浅拷贝。其余条目原样透传。
- 缺store、空列表、非Mapping条目、查询失败，全部降级为"没有序列号"。
- 查询失败会记warning日志。

## 三、它和谁协作

- 它依赖message_identity计算每条消息的身份。
- 它依赖store的get_message_seqs方法做批量查询。
- 它被app/gateway的线程路由和conversation_access调用。这些地方把检查点消息返回给客户端。
- 它是runtime/runs/worker.py里worker侧打戳器的对应物。

## 四、重要性评级

评级是5分。

理由是它修复了一个用户可感知的展示缺陷。

它还和worker侧的打戳器共享同一个打戳表达式，防止规则漂移。

但它只影响展示排序，不影响执行正确性。

降级路径保证了它失败也无害。
