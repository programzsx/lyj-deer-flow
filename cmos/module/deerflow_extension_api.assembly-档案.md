# deerflow_extension_api.assembly 档案

## 一、这个模块是干什么的

这个模块回答一个问题。一个agent是被什么组装出来的。

lead agent工厂做四件事。解析模型。渲染系统提示词。通过授权过滤工具列表。组合中间件栈。

这四件事都在一次同步调用里决定。

问题是。这些决定事后无法观察。

中间件能看到邻居。看不到提示词。

运行worker能看到图。看不到进去的是什么。

所以工厂在产出图的同时。会发一个描述符。记录这一切。

描述符的指纹让"这两次运行之间agent有没有变化"这个问题有了答案。

## 二、模块里的主要成员

- `ToolDescriptor`。一个工具的描述。包含名字、描述哈希、schema哈希、来源、MCP服务器和传输方式。存哈希不存原文。声明是身份。不是拷贝。

- `MiddlewareDescriptor`。一个中间件的描述。包含名字、模块、策略参数、贡献它的扩展名。扩展名字段很重要。贡献的中间件包在一个包装器里。所有包装器的类名共享一个。没有这个字段。两个扩展的中间件无法区分。

- `AgentAssemblyDescriptor`。整体描述符。包含命名空间、agent名、请求的模型、生效的模型、模型参数、思考开关、推理力度、基础提示词哈希、工具、中间件、延迟工具、启用技能、生效策略、构建信息。

- `AgentAssemblyDescriptor.fingerprint`。缓存属性。所有影响agent行为的字段的规范哈希。工具和技能排序。因为组装顺序无关紧要。中间件不排序。因为栈顺序决定谁包谁。两个字段故意排除。build字段。指纹回答"组装变了没"。这是比"宿主二进制变了没"更细的问题。混入build会让每次重新部署改变所有agent的指纹。requested_model字段。只有生效模型到得了提供方。请求解析到同一个生效模型不算行为差异。

- `AgentAssemblyObserver`。Protocol。`on_agent_assembled(app_store, descriptor)`。agent构建结束时同步调用。同步是因为构建本身是同步的。没有循环可等待。描述符必须在图交出去之前被捕获。实现必须便宜。不许抛错。

## 三、它和谁协作

它依赖同包的`release.py`拿canonical_hash。依赖`state.py`拿ExtensionData。

它被`contracts.py`引用。Observer协议在注册表里注册。

lead agent工厂是事实上的生产者。构建结束时发描述符。

实现Observer的扩展是消费者。

## 四、重要性评级

评级是5分。

理由如下。

它是扩展可观察性的组成部分。指纹让agent配置的变更变得可追踪。

字段取舍的设计很讲究。哪些进指纹。哪些不进。都有明确理由。

它对扩展作者有价值。对运行时正确性没有直接作用。

扣分原因。它是观察性契约。漏掉它系统照常运行。它是给运维和扩展生态提供的事实记录。
