# deerflow_extension_api.state 档案

## 一、这个模块是干什么的

这个模块定义"交给扩展的类型化存储"。

扩展在回调里需要存自己的状态。例如一个计数控。一个缓存。一个连接池。

状态存在哪。存在宿主给的ExtensionData里。

核心设计是一句话。

存储按类型做键。不按字符串做键。

这样独立的扩展不会在键上撞车。

宿主为每个scope创建一个实例。app级一个。任务级一个。

scope结束时宿主丢掉实例。

所以扩展不需要检查陈旧句柄。宿主在每次回调时把当前scope的存储交给扩展。扩展不需要自己捕获一个。

## 二、模块里的主要成员

- `ExtensionData`。核心类。扩展私有的、附着在一个宿主scope上的状态。

  - `__slots__`限制属性。省内存。防误加属性。

  - `_entries`。`{type: value}`字典。按类型做键。

  - `_lock`。RLock。保护条目字典。RLock允许嵌套获取。init回调里可以安全地组合同存储的其他状态。

  - `scope_id`属性。宿主身份。这个存储附着的scope的id。

  - `get(typ)`。按类型取。没有返回None。

  - `get_or_init(typ, init)`。取值。没有就用init创建并存入。init在锁内运行。init可以组合同存储的其他状态。重量级的懒工作要放在存进去的值自己身上。

  - `set(value)`。按值的类型存。

  - `remove(typ)`。按类型删。返回被删的值。没有返回None。

## 三、它和谁协作

它是本包的独立模块。只依赖标准库。

它被同包几乎所有模块引用。contracts、assembly、compaction、runtime_bridge都拿它做参数类型。

宿主创建实例。挂在app scope和task scope上。回调时交给扩展。

扩展是使用者。把自己的状态按类型存进去。

## 四、重要性评级

评级是4分。

理由如下。

它是扩展存状态的统一设施。所有扩展回调的参数里都有它。

按类型做键这个设计消除了字符串键撞车的问题。类型即命名空间。

scope生命周期由宿主管理。扩展不用管陈旧句柄。这个分工干净。

扣分原因。它是一个存储容器。逻辑简单。正确性风险低。它的重要性随扩展生态的存在而存在。
