# queue.py 档案

模块全名是deerflow.agents.memory.backends.deermem.deermem.core.queue。

源文件位置是backend/packages/harness/deerflow/agents/memory/backends/deermem/deermem/core/queue.py。

## 一、这个模块是干什么的

这个模块是记忆更新的队列。

队列带防抖机制。

它的工作流程是这样的。

中间件每轮对话结束时，把对话上下文丢进这个队列。

队列不立刻处理。

队列等一段可配置的防抖时间。

防抖时间内同一把键的多个上下文合并成一个更新。

防抖时间到了，定时器触发，队列开始处理。

处理就是把每个上下文交给MemoryUpdater.update_memory做提取。

队列是进程内的内存列表加一个threading.Timer。

进程退出时还在排队的项会丢。

flush_sync的排水机制在优雅关机时缓解这一点。

记忆更新是尽力而为的。

失败或丢失的更新会在下一轮对话时重新喂进来。

中间件每轮都传完整对话。

updater的水位线在失败时不前进。

所以纯内存队列就覆盖了现实的优雅部署场景。

不需要持久化层。

## 二、模块里的主要成员

（一）ConversationContext数据类

ConversationContext是一个待处理对话的上下文。

它的字段包括：

- thread_id，线程ID。
- messages，对话消息列表。
- timestamp，入队时间。
- agent_name，代理名。None时用全局记忆。
- user_id，入队时捕获的用户ID。
- trace_id，入队时捕获的请求追踪ID。
- signals，检测到的信号类集合。
- bypass_watermark，是否绕过水位线。

user_id和trace_id在入队时捕获。

捕获之后存在上下文里。

这样身份能穿越threading.Timer的边界。

ContextVar不能跨裸线程传播。

trace_id让后面的Timer线程能把它附到记忆LLM的追踪元数据上。

bypass_watermark是紧急（总结化）冲刷用的。

紧急冲刷绕过updater的索引水位线。

紧急冲刷携带的是一次性的"移除前先提取"快照。

快照自己的长度会倒退对话水位线，所以它不看也不推进水位线。

紧急上下文和同键的普通待处理更新共存。

共存而不是替换。

替换会丢掉普通更新的未提取尾部。

（二）QueueFull异常

QueueFull在非信号更新被背压拒绝时抛出。

背压规则是这样的。

队列深度达到queue_max_depth上限时，拒绝新的非信号普通项。

带信号的更新永远放行。

紧急冲刷永远放行。

同键的更新合并，不增加深度。

放行信号的理由是信号捕获重要记忆。

放行紧急冲刷的理由是它捕获即将被总结化删除的消息。

这两类都不能等下一轮再喂。

丢掉它们是真丢数据。

不是延迟。

调用方可以捕获这个异常做降级。

（三）queue_key函数

queue_key返回记忆更新目标的防抖身份。

身份是(thread_id, user_id, agent_name)三元组。

（四）MemoryUpdateQueue类

MemoryUpdateQueue是核心类。

它接受注入的config和updater。

主要方法如下。

add方法把对话加入队列。

add之后重置防抖定时器。

add_nowait方法加入并立即在后台开始处理。

它用bypass_watermark=True入队，然后调度0延迟定时器。

_enqueue_locked是入队的内部实现。

它的匹配键包含bypass_watermark。

所以紧急更新和普通更新即使同键也互相独立。

背压检查在合并检查之后。

带信号和紧急冲刷不受深度上限约束。

合并时信号取并集。

任何一次见过的信号都会保留。

_process_queue处理所有排队的上下文。

它先加锁检查。已有工作线程在处理时，置_reprocess_pending标记并返回。

避免起密集的定时器自旋。

队列非空时，把全部项取走，清空队列，逐个调用updater.update_memory。

每个更新之间睡0.5秒避免限流。

排水路径跳过这个睡眠。

排水路径的预算属于持久化，不该浪费在睡眠上。

处理完成后的finally块负责两件事。

一是记录成功和失败计数。分计数让运维能区分"排空了"和"每个提取都持久化了"。

二是在锁内处理重跑标记。处理期间来了新工作时立即重跑。

flush方法强制立即处理。用于测试或优雅关机。

flush_sync方法是有超时上限的尽力而为同步冲刷。

flush_nowait方法调度立即处理但不等待。

cancel_by_agent方法按作用域丢弃待处理上下文，不处理它们。

clear方法清空队列。用于测试。

pending_count和is_processing属性报告状态。

## 三、flush_sync处理的两场竞态

这是这个模块最精细的部分。

（一）在途工作线程竞态

防抖定时器已经触发时，_process_queue的工作线程正在做LLM调用。

它已经把上下文从队列取走了。

这时队列是空的，_processing是True。

单纯的flush会看到正在处理就什么都不做，然后报告成功。

但那个工作线程还在跑，退出时会被杀。

它手里的上下文就丢了。

所以flush_sync先join在途的工作线程。

join的等待受剩余预算约束。

（二）flush本身的失败

flush做同步LLM调用，调用可能抛异常。

成功只在正常路径上记录。

返回值要匹配"真正完成"的语义。

所以flush_sync只有在排水真正结束（队列空、没有工作线程在跑、flush没抛异常）且在预算内时才返回True。

（三）共享预算

第（1）步的join和第（3）步的排水共享同一个deadline预算。

慢的在途工作线程可能耗尽预算。

剩下的排水步骤就变成空操作。

所以timeout必须同时覆盖慢的在途工作线程和剩余队列。

预算内没排干的尾部会被丢。

这和无冲刷的失败方向一样，只是范围限于尾部。

## 四、cancel_by_agent的作用域语义

cancel_by_agent只取消待处理的防抖上下文。

它匹配(agent_name, user_id)。

匹配只针对还坐在_items里的项。

已经被在途工作线程取走的上下文故意不碰。

中断进行中的LLM调用属于持久化发件箱的事。

不属于这个内存防抖队列。

user_id为None时只取消legacy无用户根。

这镜像了存储层的语义。

None对None，不是"所有用户"。

更广的取消必须遍历已知的用户作用域。

## 五、它和谁协作

（一）它依赖谁

它依赖DeerMemConfig拿防抖秒数和队列深度上限。

它类型上引用MemoryUpdater。

（二）谁调用它

MemoryMiddleware在每轮对话后调用add。

summarization_hook通过add_nowait或flush做紧急冲刷。

DeerMem本体在关机时调用flush_sync。

Gateway关机路径预留超时给规范记忆冲刷。

MemoryUpdater由队列调用。

## 六、设计意图

这个模块体现一个核心权衡。

权衡的双方是简单性和数据安全。

一方是纯内存队列。

纯内存队列不需要持久化层。

另一方是数据丢失。

进程退出丢待处理项。

这个权衡的解法是失败方向的设计。

记忆更新是尽力而为的。

丢失的更新下一轮会重新喂进来。

中间件每轮传完整对话。

水位线失败不前进。

所以丢失只是延迟，不是真丢。

只有两种情况不能等下一轮。

一种是带信号的更新。

一种是紧急冲刷携带的即将删除的消息。

这两种在背压下永远放行。

这个设计让内存队列成立。

## 重要性评级

评级是7分（满分10分）。

理由如下。

这个模块是被动记忆捕获的调度中心。

中间件模式是默认模式。

所有被动记忆更新都经过这个队列。

防抖合并把同键的多轮对话合成一次提取。

这直接控制提取LLM的成本。

背压、信号放行、紧急冲刷共存这些设计决定了"重要记忆不丢"。

flush_sync的关机排水防止滚动部署丢记忆。

它的弱点是纯内存。

崩溃时待处理项全丢。

靠下一轮重喂兜底。

用户停止对话时重喂不会发生。

那种情况下的尾部记忆会丢。

这是已接受的设计取舍。

综合来看，它是记忆系统的关键组件。

评7分。
