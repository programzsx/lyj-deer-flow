# deerflow_extension_api.placement 档案

## 一、这个模块是干什么的

这个模块解决"扩展的中间件在宿主的中间件栈里坐在哪"。

背景是这样的。

扩展贡献中间件时。需要声明自己想坐在什么位置。

直接声明位置索引是不行的。例如"把我放第3层"。

宿主的栈会重构。位置索引会失效。

这个模块的办法是声明"语义保证"。

例如"我需要观察原始的工具返回"。

而不是"把我放在第3层"。

核心洞察是一句话。位置索引只在它实现的钩子链上有意义。模型轴的"最外层"和工具轴的"最外层"是两回事。按轴加端点声明。消除歧义。同时让宿主保持重构栈的自由。

## 二、模块里的主要成员

- `Placement`。放置声明的五种枚举。

  - `MODEL_LOGICAL`。模型轴外端。保证在重试和错误处理之外。宿主底层重试多少次。它只触发一次。

  - `MODEL_PHYSICAL`。模型轴内端。保证在每个会变换请求的中间件之内。每次真实的提供方调用都触发它。重试会重新进入。

  - `TOOL_VISIBLE`。工具轴外端。保证在截断、清洗、错误包装之外。观察模型最终看到的东西。

  - `TOOL_RAW`。工具轴内端。保证紧贴真实的可调用边界。观察工具在任何处理之前的原始返回。

  - `STANDARD`。没有前后处理要求。和其他STANDARD贡献者的相对顺序不保证。

- `AgentScope`。Flag枚举。LEAD、SUBAGENT、BOTH。声明中间件作用于哪种agent。

- `AgentBuildContext`。扩展决定贡献什么时能知道的信息。包含scope、agent名、模型名、策略快照。

- `MiddlewarePlacement`。一个中间件加它的放置声明。middleware类型是Any。保持本模块导入轻量。宿主在注入时校验类型。

## 三、它和谁协作

它依赖同包的`contracts.py`拿HostPolicySnapshot。

它被`contracts.py`的MiddlewareContributor引用。

宿主的中间件栈组装逻辑消费Placement声明。决定每个中间件的注入位置。

扩展是声明方。

## 四、重要性评级

评级是5分。

理由如下。

它解决了一个真实的架构问题。扩展如何在不耦合宿主内部结构的前提下精确表达放置意图。

语义保证替代结构位置。这个设计让宿主保持重构自由。让扩展保持稳定。

五种放置的语义文档写得很清楚。每种保证什么、不保证什么。

扣分原因。它只在扩展贡献中间件时生效。是类型契约。没有运行时逻辑。核心中间件链不经过它。
