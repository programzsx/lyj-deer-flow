# deerflow.runtime.keyed_lock 档案

## 一、这个模块是干什么的

这个模块提供"按key加锁"的表。

场景是这样的。

多个运行要同时操作同一条线程。同一条目标。同一个资源。

按key加锁可以让同一个key的操作串行化。不同key的操作并行。

普通的做法是维护一个`{key: Lock}`字典。但这个做法有个漏洞。

锁用完之后没人删。字典会无限膨胀。

删早了也不行。新调用者会建第二把锁。绕过已经排队的等待者。

这个模块用"参与者计数"解决。

进入之前计数加一。离开之后计数减一。

计数为零且锁没人持有。才回收这个条目。

这保证条目在最后一个持有者或等待者离开前始终可见。

## 二、模块里的主要成员

- `AsyncKeyedLockTable`。asyncio版本。服务async调用者。`hold(key)`是一个async上下文管理器。持有当前事件循环的锁。

  - 它的表按事件循环分桶。`asyncio.Lock`一旦被争用就绑定到特定事件循环。不同线程里的循环共享一张表会出问题。所以每个循环有自己的条目。

  - 一个`threading.Lock`保护注册表本身。异步临界区绝不持有这个保护锁。

- `KeyedLockTable`。线程版本。服务worker线程上的阻塞临界区。`hold(key)`是普通上下文管理器。阻塞调用线程。

  - 条目结构更简单。一张`{key: entry}`字典。一个保护锁。

- 两个类共享同一套设计。checkout时计数加一。checkin时计数减一。参与者归零且锁空闲时回收条目。回收前还会确认字典里的条目还是自己。防止误删后来者。

## 三、它和谁协作

它只依赖标准库。asyncio、threading、weakref、contextlib。

它被`runtime/goal.py`依赖。目标读改写用`AsyncKeyedLockTable`串行化。

worker和事件存储里同key串行化的需求可能用它。但journal和事件存储有各自的锁域。

## 四、重要性评级

评级是5分。

理由如下。

它是一个干净的并发原语。147行。设计正确。文档清楚。

参与者计数加弱回收这个模式。解决了朴素字典锁的两个经典漏洞。

按事件循环分桶处理了`asyncio.Lock`的循环亲和性。这个坑很多人不知道。

扣分原因。它是底层原语。业务语义不在这里。当前直接依赖它的模块不多。goal模块是主要用户。

它是那种"代码很短但写对很难"的模块。评分中游。因为它的价值靠使用者体现。
